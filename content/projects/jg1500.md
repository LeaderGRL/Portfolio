## THE PORTFOLIO BECAME A SYSTEMS PROJECT

JG-1500 started with a fairly simple visual idea: make the portfolio feel like a physical computer with a curved CRT, real controls and a chassis that occupies the browser window.

The visual part was only the beginning. A project page still needs selectable text, links, keyboard navigation, images, videos, 3D content, responsive layouts, browser history, accessibility and useful URLs. Putting scanlines over a normal webpage would have been much easier, but it also would have stopped being convincing the moment anything moved.

So I treated the display as an actual display pipeline.

The result is a small web runtime where terminal screens and long-form documents become pixel sources for the same physical CRT. The interface looks deliberately old; the architecture underneath it is not.

## ONE PHYSICAL CRT

There is one persistent display path for the machine.

::pipeline{label="DISPLAY PIPELINE"}
TERMINAL SCREENS | TERMINAL RASTER SOURCE
PROJECTS + ARTICLES | DOCUMENT RASTER SOURCE
DISPLAY PIPELINE | SELECTS THE ACTIVE PIXEL SOURCE
CRT WEBGL | PERSISTENCE + CURVATURE + SCANLINES + PHOSPHOR COMPOSITE
PHYSICAL GLASS | FINAL DISPLAY INSIDE THE CHASSIS
::

Terminal pages render through the terminal rasteriser. Projects and articles render through a separate document rasteriser. `DisplayPipeline` decides which source is currently feeding the tube, and the CRT compositor processes the result.

That distinction matters. A screenshot, a code block and a terminal heading can all belong to different document systems while still looking like they exist behind the same glass.

Local media follows the same idea. Video frames and local Three.js scenes can be painted into the document source before the CRT pass. Cross-origin iframes are the awkward exception: browsers do not allow their pixels to be sampled into a canvas, so those integrations are mounted separately and receive matching CRT optics instead.

The browser security model won that argument.

## A DOCUMENT ENGINE INSTEAD OF PROJECT-SPECIFIC PAGES

Projects and articles are authored as Markdown, but the runtime never treats them as arbitrary HTML blobs.

At build time, `plugins/content.js` parses front matter and converts the body into a typed block model shared with `src/document/schema.js`. Unknown directives fail the build instead of quietly disappearing.

::system{columns=2 label="DOCUMENT VOCABULARY"}
TEXT | HEADINGS · PROSE · LISTS · CODE · NOTES
EDITORIAL | FACTS · SYSTEMS · PIPELINES · TIMELINES
MEDIA | IMAGES · VIDEO · AUDIO · GALLERIES · COMPARES
INTERACTIVE | LOCAL 3D · YOUTUBE · SKETCHFAB · IFRAMES
::

The renderers are registered generically. Adding ASTRO, LEAK or JG-1500 should mean writing content and adding assets, not creating `src/jg1500.js` and teaching the runtime another special case.

The visible document is rasterised into the CRT, while a synchronized semantic DOM mirror keeps links, focus, scrolling and native media behavior usable by the browser. When keyboard focus enters that transparent semantic layer, the runtime projects the focus state back onto the visible CRT.

It is a slightly strange arrangement, but it lets the page behave like a webpage without visually becoming one.

## RESPONSIVE WITHOUT TURNING THE COMPUTER INTO A RECTANGLE

The responsive problem was not "make the div narrower". The chassis has authored proportions, the CRT has a curved safe area, controls need usable hit targets and mobile screens can be much taller than the machine geometry.

JG-1500 therefore separates physical machine geometry from the surrounding material. Layout code chooses the correct desktop, portrait or landscape composition and scales the functional machine predictably, while the outer chassis material fills the viewport independently.

::system{columns=2 label="RESPONSIVE MODES"}
DESKTOP | AUTHORED WIDE CHASSIS COMPOSITION
PORTRAIT | DEDICATED PORTRAIT CHASSIS ASSETS
LANDSCAPE MOBILE | COMPACT WIDE CONTROL LAYOUT
FULL SCREEN | GLASS EXPANDS AND CHASSIS STEPS ASIDE
::

Full screen is its own display mode rather than a CSS zoom. The document reflows, the raster source follows the viewport, the CRT effects stay active and the reading position is preserved when the browser changes size or orientation.

That last part is less glamorous than phosphor bloom and considerably easier to notice when it is wrong.

## ASSETS ARE BUILT, NOT HAND-WIRED

The chassis is assembled from authored source renders under `assets/src/`. A Python-assisted asset pipeline prepares the runtime sprites in `assets/build/`, while Vite fingerprints imported assets for production caching.

Large runtime media stays outside the JavaScript bundle under `public/media/`. Project content references those files through the document system, so adding a video does not turn it into a base64 surprise inside the application bundle.

::pipeline{label="PRODUCTION BUILD"}
SOURCE ASSETS | AUTHORING RENDERS + CONTENT + MEDIA
ASSET PIPELINE | GENERATES RUNTIME CHASSIS ASSETS
VITE | BUILDS FINGERPRINTED APPLICATION OUTPUT
SEO GENERATOR | BUILDS ROUTE-AWARE NGINX CONFIGURATION
RUNTIME TESTS | VALIDATE THE PRODUCTION OUTPUT
DOCKER | COPIES DIST + GENERATED NGINX INTO THE FINAL IMAGE
::

The production image therefore contains the built site and the web-server configuration it was tested with, rather than rebuilding behavior after validation.

## TESTING THE MACHINE AT THE LEVEL USERS BREAK IT

The test suite is split by responsibility.

Fast runtime checks cover document schemas, navigation, layout decisions, display behavior, article parsing, controls, SEO generation and other deterministic logic. Playwright then runs the real portfolio across Chromium, Firefox, WebKit and a mobile Chromium profile.

The browser tests also exercise accessibility with Axe and keep traces, screenshots and video when a failure needs investigation.

Visual regressions have a separate deterministic Chromium project. It freezes only test-time sources of variation such as the CRT clock, static/degauss state and terminal clock, then compares five critical layouts:

- desktop at 1440×900;
- Pixel 7-class portrait at 412×915;
- iPhone-class portrait at 393×852;
- tablet portrait at 768×1024;
- mobile landscape at 915×412.

The production CRT still runs normally. The deterministic mode exists only so a screenshot test can tell the difference between a layout regression and a different frame of animated noise.

## URLS AND SEO STILL HAVE TO BE BORING

The runtime uses real routes such as `/projects/jg1500` and keeps browser Back/Forward behavior through the History API.

Client-side metadata is enough for a person navigating inside the app, but social crawlers may inspect the first HTML response without running the application. The build therefore generates route-aware Nginx metadata maps from the same content source used by the portfolio.

Each known project/article route can receive its own title, description, canonical URL and Open Graph metadata before JavaScript executes. Deep links still fall back to the SPA at the server level, so opening a project URL directly restores the same runtime state as navigating to it through the CRT.

## DEPLOYMENT IS PART OF THE BUILD

The Docker image uses a multi-stage build. Node and Python handle assets, application compilation and runtime validation; the final stage serves only the production output through Nginx.

CI repeats the important parts on pull requests: build, runtime tests, browser suites and generated Nginx validation. Publishing the production image is reserved for successful changes on `master`.

That pipeline is intentionally unexciting. After spending enough time making a browser convincingly imitate an old CRT, I am happy for deployment to behave like a normal computer.

## WHAT I WOULD KEEP FROM THIS PROJECT

The most useful decision in JG-1500 was separating **what a document means**, **how it becomes pixels**, and **how those pixels are displayed**.

That separation made it possible to add richer project pages, local 3D, responsive modes, semantic focus, deep links and visual regression testing without replacing the physical-display model each time.

There are trade-offs. Rasterising documents is more complex than styling normal DOM content, cross-origin integrations need a separate path, and responsive work has to respect both browser ergonomics and authored machine geometry.

For this project, those costs are the point. The portfolio is meant to show engineering work, and the machine presenting it became one more piece of that work.
