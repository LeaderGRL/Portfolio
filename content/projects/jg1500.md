## WHY I BUILT IT THIS WAY

JG-1500 is my portfolio, but I use it as a technical project in its own right.

I wanted the site to behave like a physical computer rather than a normal page with a CRT filter on top. The curved screen, controls and chassis therefore have to coexist with normal web requirements: keyboard navigation, selectable content, links, media, browser history, accessibility and responsive layouts.

That led to a simple rule for the architecture: the CRT is the display output, not decoration around the page.

## ONE DISPLAY PIPELINE

The application has one persistent CRT output. Terminal screens and long-form documents use different raster sources, but both end up in the same WebGL compositor.

`DisplayPipeline` selects the active source. The CRT pass then applies curvature, scanlines, persistence and the phosphor treatment before the image is shown behind the physical glass.

Project and article pages can contain normal text, code, images, local video and local Three.js scenes. Those elements are rendered into the document source before the CRT pass when the browser allows it.

Cross-origin iframes are handled separately because the browser does not allow their pixels to be sampled into a canvas. They stay as native browser elements and receive matching visual treatment instead of being forced through the raster pipeline.

## DOCUMENTS ARE DATA, NOT CUSTOM PAGES

Projects and articles are written in Markdown. During the build, `plugins/content.js` parses their front matter and body into the typed block model shared with `src/document/schema.js`.

The document engine supports prose, headings, lists, code, notes, images, galleries, comparisons, audio, video, local 3D scenes and external embeds. Unknown directives fail the build.

The important part is that projects do not get their own runtime implementation. Adding a new case study should mean adding content and assets, not another project-specific JavaScript module.

The visible document is rasterised for the CRT, while a synchronized semantic DOM layer keeps native links, focus and accessibility available to the browser. Focus changes in that semantic layer are projected back into the visible CRT so keyboard navigation still has a visible state.

## RESPONSIVE MACHINE GEOMETRY

The responsive layout cannot be solved by scaling one desktop image. The screen aperture, control positions and chassis proportions are part of the interaction surface.

Desktop, portrait and mobile landscape therefore use authored chassis compositions with measured apertures. The layout engine chooses the closest profile, fits the functional machine to the viewport and lets the surrounding chassis material fill any remaining area.

Portrait has dedicated assets because stretching the desktop composition produced the wrong proportions. Mobile landscape uses a compact control layout so the CRT and hardware remain usable on short screens.

Full screen is handled as a separate display mode. The chassis is removed from the composition, the document raster follows the viewport and the CRT renderer keeps the same display treatment. Reading position is preserved through resize and orientation changes.

## ASSET AND BUILD PIPELINE

Source renders live under `assets/src/`. A Python-assisted pipeline generates the runtime chassis assets in `assets/build/`, then Vite fingerprints the imported output for production.

Large media files stay under `public/media/` instead of being bundled into the JavaScript payload. The document system references them directly.

The production build also generates the route-aware Nginx configuration used by the deployed site. The Docker build runs the asset pipeline, builds the application, runs the runtime checks and copies the tested `dist/` output into the final Nginx image.

## TESTING

I split the tests by the kind of failure they are meant to catch.

Runtime checks cover document parsing, layout selection, navigation, display behavior, controls, SEO generation and the application controller boundaries. Playwright covers the rendered application in Chromium, Firefox, WebKit and a mobile Chromium profile.

The browser suite also checks accessibility and interaction paths such as keyboard navigation, full screen, power state, article scrolling and media behavior.

Visual regression tests run separately in a deterministic Chromium configuration. They cover 1440×900 desktop, 412×915 and 393×852 phone portraits, 768×1024 tablet portrait and 915×412 mobile landscape. Test-only animation sources are frozen so a CRT noise frame does not look like a layout regression.

## ROUTES, SEO AND DEPLOYMENT

Projects use real URLs such as `/projects/jg1500`, with browser Back and Forward handled through the History API.

Client-side metadata is updated during navigation, but direct links also need useful metadata before JavaScript starts. The build generates Nginx maps from the same project and article content so known routes receive their own title, description, canonical URL and Open Graph values in the initial response.

CI runs the build, runtime checks, browser suites, visual regression tests and Nginx validation on pull requests. The production image is published only after successful changes on `master`.

## WHAT THIS PROJECT TAUGHT ME

The most useful architectural boundary is the separation between document meaning, document rasterisation and physical display.

That separation made it possible to add new content types, local 3D, responsive layouts, semantic focus, deep links and visual regression tests without replacing the CRT renderer.

The cost is extra complexity compared with a conventional DOM-first portfolio. Rasterised documents need a semantic mirror, cross-origin content needs a second path and responsive work has to account for both browser ergonomics and authored machine geometry.

For JG-1500, that trade-off is deliberate. The portfolio is not only a place where I show engineering work; part of the engineering work is the portfolio itself.
